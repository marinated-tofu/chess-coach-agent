Product loop

The adaptive learning loop

Every feature supports one cycle: import → detect weaknesses → practice → grade → adapt.

ImportChess.com / Lichess sync or PGN analyze
→
DetectStockfish + Lichess-style win-chance loss
→
ExplainDeterministic theme templates + BM25 lessons
→
PracticePydantic AI ranks + writes quiz copy (optional)
→
GradeStockfish move evaluation — never waits on LLM
→
AdaptSpaced repetition + player memory
Chess.com / Lichess / PGN │ ▼ Durable sync + PGN parser + Stockfish detectors │ ├─► games, analyses, critical moments ──► Progress analytics │ ▼ Practice session from stored mistakes │ ├─► PydanticAI agent (if OPENROUTER_API_KEY) ranks + quiz copy ├─► fallback: deterministic rank + template / LLM quiz copy │ ▼ Board quiz ──► Stockfish grading ──► review schedule ──► player memory ▲ └──────────── adaptive difficulty by theme ────────────┘
System design

Architecture layers

Frontend (React + Vite)

  • TanStack Router — /, /games, /practice, /progress, /quality
  • TanStack Query — server state for progress, training sessions
  • WorkspaceContext — player, platform, sync status, analysis cache in sessionStorage
  • No LLM in the browser — only REST calls to /api/*

Backend (FastAPI + Python)

  • api.py — health, analyze, feedback, monitoring, LLM status
  • adaptive_api.py — sync, games library, training, progress
  • analysis.py — deterministic game analysis pipeline
  • practice_agent.py + llm.py — Pydantic AI practice path
  • engine.py — Stockfish (authoritative for chess claims)

Storage

  • Postgres in production (Render)
  • SQLite local fallback
  • SQLAlchemy models + Alembic migrations
  • Players keyed by (platform, username)
  • pgvector for lesson chunk embeddings (retrieval eval, not live chat)

Retrieval & memory

  • BM25 default for lesson snippets attached to analyses
  • Player memory recomputed from imports, moments, quiz attempts
  • Raw PGNs/FENs stored relationally — not embedded as prose
  • 20-query retrieval benchmark in retrieval_evaluation.py

Pydantic AI

The practice agent

Pydantic AI (pydantic_ai) wraps OpenRouter as an Agent with twelve tools and a structured output schema CoachingOutput.

Agent factory — llm.py

from pydantic_ai import Agent, RunContext from pydantic_ai.models.openai import OpenAIChatModel def create_coach_agent() -> Agent[CoachDependencies, CoachingOutput]: return Agent( _openrouter_model(), # OpenRouter via OpenAI-compatible API deps_type=CoachDependencies, # shared state: platform, username, plan_id, tools_used output_type=CoachingOutput, # Pydantic schema for final LLM response instructions=COACH_INSTRUCTIONS, tools=[ # 12 tools — see table below search_chess_principles, inspect_critical_moments, inspect_player_moments, inspect_position, build_training_drill, inspect_game, compare_moves, rank_practice_moments, generate_position_quiz, evaluate_candidate_move, build_training_session, write_quiz_copy, ], retries=1, )

Twelve agent tools

ToolFilePurpose
search_chess_principlesllm.pyBM25 retrieval from curated lesson chunks
inspect_critical_momentsllm.pyEngine facts from current or stored moments
inspect_positionllm.pyStockfish + checks/captures for a FEN
build_training_drillllm.pyDrill text from dominant weakness theme
inspect_gamecoach_tools.pyOne persisted game + its moments
inspect_player_momentscoach_tools.pyStored critical moments for player
rank_practice_momentscoach_tools.pyLLM-rank moments by weakness → deps.ranked_moment_ids
write_quiz_copycoach_tools.pyLLM quiz prompt + hint per position
compare_movescoach_tools.pyStockfish compare candidate SANs
generate_position_quizcoach_tools.pyQuiz panel from stored moments
evaluate_candidate_movecoach_tools.pyGrade a candidate move
build_training_sessioncoach_tools.pyCreate DB plan → deps.plan_id

Structured output — CoachingOutput

class CoachingOutput(BaseModel): answer: str # concise coaching answer (Markdown) evidence: list[str] # grounded facts from tools / engine recommended_move: str | None principle: str drill: str confidence: float # 0..1

In practice sessions, the important side effects are usually the tools (creating plan_id, writing quiz copy), not the final CoachingOutput text returned to the caller.

Production entry — practice_agent.py

POST /api/training/sessions │ ▼ run_practice_agent(session, platform, username, theme, position_count, moment_id) │ ├─ moment_id set? ──YES──► build_training_session() + template copy [NO agent, ~instant] │ └─ moment_id null + OPENROUTER_API_KEY? │ ▼ agent = create_coach_agent() await agent.run(PRACTICE_AGENT_PROMPT, deps=CoachDependencies(...)) │ ├─ LLM picks tools in a loop (inspect → rank → build → write_quiz_copy) ├─ deps.plan_id set by build_training_session tool └─ returns CoachingOutput │ ▼ training_session_view(plan_id) → JSON to frontend On failure → deterministic rank + apply_llm_quiz_copy (raw OpenRouter, no agent loop)

Monitoring — the only eval-adjacent UI feature

/quality is not in the sidebar. Open /quality directly. It aggregates JSONL events from normal usage:

User actionEvent logged
Sync gamesgames_sync_*, analysis_completed
Thumbs up/down on reviewmoment_feedback
Start practicetraining_session_created, practice_agent_completed
Submit move in practicequiz_attempted
Stale metrics: llm_calls, token counts, and chat latency on the dashboard come from retired chat_completed events. Use practice_agent_runs and practice_agent_fallback_rate for current LLM telemetry.

Client state (WorkspaceContext)

Player, platform, and up to 25 analyses live in sessionStorage. Server DB is authoritative for sync, training, and progress. Game review reads the browser cache — deep links without prior sync show “Review unavailable.”
